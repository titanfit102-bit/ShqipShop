## 2026-11-09 — F08 Stage 12A: native refund policy and uncertain-PSP-outcome design review (SOURCE VERIFIED / DESIGN PROPOSED; NOT IMPLEMENTED)

**Verified pinned source:** Medusa **v2.22.0**, [Payment Module refundPayment_](https://github.com/medusajs/medusa/blob/v2.22.0/packages/modules/payment/src/services/payment-module.ts#L1054-L1184), [refundPayment and provider call](https://github.com/medusajs/medusa/blob/v2.22.0/packages/modules/payment/src/services/payment-module.ts#L929-L989), [provider dispatch](https://github.com/medusajs/medusa/blob/v2.22.0/packages/modules/payment/src/services/payment-module.ts#L1187-L1209), [Admin route](https://github.com/medusajs/medusa/blob/v2.22.0/packages/medusa/src/api/admin/payments/%5Bid%5D/refund/route.ts), [Admin validation](https://github.com/medusajs/medusa/blob/v2.22.0/packages/medusa/src/api/admin/payments/validators.ts), [refund model unique index](https://github.com/medusajs/medusa/blob/v2.22.0/packages/modules/payment/src/models/refund.ts). These are SOURCE READBACK findings, not a production fix.

### Why the confirmed P0 persists

- The native module **already** acquires PostgreSQL `payment FOR UPDATE` inside `refundPayment_`, re-reads captures and refunds under the lock, resolves matching `idempotency_key`, then reserves a native `Refund(PENDING)` record. Provider calls occur **after** that transaction. The native schema already has a unique index on `(payment_id, idempotency_key)` for non-null keys. Replacing this with a second application ledger would introduce a second authority.
- The amount comparison is `captured - (refunded + requested) < -currencyEpsilon`; for `ALL` (zero decimals), `currencyEpsilon = 1`. An **exact +1 ALL** excess is NOT rejected by that comparison. Independent 11I/J/O/P unguarded mock sentinels reproduced the persisted financial defect. Stages 11W/X/Y/Z test bounded behavior of a **disposable, serial read-before-write CI middleware only**; no production code is repaired.
- Under an ambiguous provider-side failure, the current native `refundPayment` catch path marks `FAILED` and soft-deletes the refund after an exception from `refundPaymentFromProvider_`. The provider might have completed the refund before losing its acknowledgment. A subsequent NEW key could then be treated as available capacity. This is a **source-supported failure-mode hypothesis, NOT verified real-PSP double settlement**. The native 15-minute stale-PENDING recovery uses the same key but only works safely if the PSP honors durable idempotency.

### Recommended minimal corrective boundary (PROPOSED, separate authorization required)

1. Prefer a verified upstream Medusa fix on a pinned version; if unavailable, separately review a minimal version-pinned native Payment Module patch. The correctness check belongs inside the **same native `refundPayment_` PostgreSQL transaction**, AFTER the payment-row lock and locked-DB reload, **AFTER same-key replay resolution**, but BEFORE native refund creation/resumption and PSP dispatch. Do not rely on Admin HTTP middleware (TOCTOU and bypass via internal workflows), a cross-transaction lock, a shared Redis-only lock, or separate balances table.
2. For ALL only, require **explicit, positive, exactly integral, safely representable** request amounts; parse persisted monetary values without lossy `Number()` rounding. Define `C = sum(authoritative captured rows)`, `R = sum(non-deleted succeeded + pending + unresolved native refund rows, excluding the matching operation being resumed)`, `A = requested positive integer ALL`. Reject if `C <= 0`, negative/ambiguous values, `R > C`, or `A > C - R`. Exact equality is allowed. Do **NOT** reuse an epsilon of 1. Preserve other-currency behavior until individually reviewed and tested; do not globally change currency precision.
3. Resolve `(payment_id, idempotency_key)` under the same lock first: identical settled key + amount returns the original result with **zero new PSP effect**; same key + different amount rejects; unresolved/pending operation never causes a new refund with a different key while its real provider result is unknown. Every requested refund must have a stable server-validated operation key. Preserve Medusa's native unique index; do not create parallel finance authority.
4. Authenticate and authorize **before replay**: server-derived active merchant, finance permission, Admin actor, payment owner and collection/tenant association. A valid Admin JWT alone is not proof of permission to refund another merchant's payment. No client-supplied merchant ID or request header may establish financial authority.
5. Treat provider timeout, connection reset or ambiguous acknowledgment as **UNKNOWN/PENDING until verified**, not automatically as a definitive failure that releases refund capacity. Reconcile against the PSP using a stable durable operation key/provider reference; accept only verified signed callbacks or authenticated PSP status queries. Deduplicate webhooks and audit transitions. If the PSP cannot guarantee keyed idempotency and authoritative reconciliation, **disable automated live refunds** rather than retrying speculative financial effects. Any changes to Medusa native `FAILED`/soft-delete behavior need separate review.
6. Persist/operate solely on the existing authoritative Medusa `payment/capture/refund` rows. Outbox records may coordinate delivery/reconciliation but must remain **derivative**, never a separate spendable balance. Do not use the Stage11R/S disposable tables as a production model or wire them to a real provider.

### Acceptance and release evidence, not achieved

| Boundary | Required independent proof |
| --- | --- |
| Exact ALL | direct module + singular/plural workflow + true Admin HTTP: zero capture/zero/negative/fractional/unsafe values and **exactly +1 ALL** reject with unchanged native PostgreSQL rows; legitimate partial/exact-full succeed |
| Concurrency | two API processes, same and distinct keys with a deterministic in-flight barrier at native writer lock; exactly one eligible amount reservation; different payment remains independent |
| Key replay | settled same key/amount returns same native record; mismatched amount/key rejected; key remains stable after restart and cross-process retry |
| Provider uncertainty | PSP **sandbox** (not manual mock): ACK-loss after provider success, same-key retry, unknown outcome hold, authenticated reconciliation and duplicate/out-of-order signed webhooks; never double settlement |
| Merchant and identity | active finance role + server-owned merchant/payment matching required; customer, non-finance staff, revoked actor, foreign tenant and forged scope all denied, unchanged finance ledger |
| Durability and supply chain | pinned-source/patch diff review, rollback, repeatable clean CI, backup/restore, audit trail and independent P0 security review; original 11I/J/O/P assertions MUST remain intact and must pass due to actual correction rather than being skipped |

**Decision status:** no upstream upgrade, vendor patch, production flow/schema, merchant permissions, PSP integration, deploy or main merge authorized or implemented. Existing PR #12 stays Draft. **T05/S13 P0; RG-01/02/03, G3/G5 BLOCKED.** Next: read official fix availability and compare minimal native patch vs pinned upgrade; obtain separate approval before changing production-capable finance behavior. Only disposable CI/non-financial documentation may proceed under existing authorization.

## 2026-11-09 — Stage 11N refund workflow trust-boundary contract (PROPOSED, NOT DEPLOYED)

A future permitted refund path must resolve merchant **from trusted Medusa deployment/server identity**, and operator from **verified Admin authentication + effective role/policy**, not client tenant IDs, publishable keys, or request-body claims. Authorization to request a refund must precede any ledger read, reserve, provider dispatch or idempotency replay. A positive amount must be an exact integer in the settlement currency (for ALL, no decimal rounding tolerance) and must not exceed the captured less successful/pending-reserved amount. Under a merchant/payment row-level lock, persist a unique operation ID, actor, exact amount and dispatch/outbox record atomically; commit BEFORE any external PSP call. Workers must claim a queued dispatch once, never blindly resend on ambiguous network/ack failure; keep the reserve pending until authenticated PSP record lookup or signed provider event has been reconciled to payment/merchant/amount/ref. Verify worker lock expiry, provider idempotency behavior, notifications and operations audit without PII leakage. Production requires separate design/approval and provider-specific sandbox tests. ## Boundaries and default-deny contract

1. **Tenant routing:** authenticated operator/control plane resolves merchant from trusted domain/config, not a client-supplied tenant ID. Pilot recommendation: independent Medusa app, PostgreSQL DB/role, Redis service/credentials, sessions, event workers, object storage and secrets **per merchant**. Publishable Store API keys and sales channels are **not authorization** for private data. Keep control plane out of regular order/PII pathways.
2. **Store API:** identity + tenancy + resource ownership checks at every private read/write and webhook. Guest receipts require an unguessable secondary capability, never order ID alone; rate-limit attempts and minimize PII. Admin endpoints need role/action/resource authorization, anti-IDOR tests, no browser-derived tenant grants. Separate privileged admin/operator access.
3. **Backend service:** Node Medusa reads prices, currency, stock, discounts and final totals from server-side state; reject stale quote, replay and payment mismatch before order/payment mutation. Hooks alone are not an atomic payment lock. Use transaction/locking, idempotency and uniquely constrained writes at the correct workflow boundary; do not authorize PSP charges based on client totals or indicative FX.
4. **Data/Redis:** tenant-local least privilege, encrypted connections in production, DB roles and Redis ACL; never share caches/keys/events/workers without verified namespace+credential boundary. Backups encrypted, access-limited, restore tested to isolated target; lifecycle/retention/PII deletion defined and audited.
5. **Clients:** native public publishable key only, HTTPS certificate validation, disable cleartext in production, no private data/token in logs or URLs. Replace AsyncStorage JWT with secure Android Keystore/iOS Keychain-backed design; clean all private caches on identity/merchant change and sign-out. Protect exported components, deep links, clipboard/screenshot leakage and backup. Android `allowBackup=false` is present; **release currently debug-signed**, not shippable.
6. **PWA/pilot:** session cookies Secure/HttpOnly/SameSite in deployed HTTPS, state-changing CSRF checks and origin validation, CSP/XSS/SQLi defenses, no private cache, access control enforced server-side. Existing FastAPI in-memory rate limiting is pilot-only; distributed edge API limits are pending.
7. **Edge/operations:** verified TLS/HSTS, per-tenant CORS/domain/CSRF separation, WAF and layered rate limits, DDoS capability where hosted, alerting on auth abuse/data access anomalies, structured minimal-redaction audit records, rotation procedures, scoped incident response and tested recovery. Do not publicly store internal topology, incident details or secrets.
8. **Supply chain:** lockfile reproducibility, SHA-pinned GitHub Actions, least-privilege GitHub workflow tokens and non-persistent checkout, reviewed dependency updates/CI findings, verified release signing/attestation/SBOM. Never run untrusted PR code with long-lived credentials or `pull_request_target` privileges.
